# Release — ship Starkeep to friends and family

Committed at execution as `docs/plans/2026-10-13-release.md`. Architecture doc row "Release"
(added 2026-10-08): Windows installer on GitHub Releases, Tauri auto-updates, the web version on a
free host (also the Mac answer).

## Context

M0–M5 built the app; it has only ever run on Lucas's machines against the local stack. Nobody else can
use it: there is no hosted web version, no installer anyone can download, and no way for an installed
app to learn about a new version. This milestone makes Starkeep something Lucas can send a link to,
and keeps every copy current afterwards with no effort from the people using it.

### Decided with Lucas (2026-10-13)

| Question | Decision |
|---|---|
| Repository | **Make it public.** Installer and update files are served by GitHub Releases, which only serves the public from a public repo. History checked: no secrets ever committed (only `sb_secret_...` placeholders). Accepted: code, plans, notes and the personal Gmail on 42 old commits become visible. Bonus: free secret scanning / push protection, unlimited Actions minutes. |
| Web host | **Vercel** (free Hobby plan: personal, non-commercial; 100 GB/month — 10 friends ≈ 0.1%). Supersedes the architecture doc's Cloudflare Pages. |
| Desktop updates | **Notice + one click.** The app checks by itself; shows "Starkeep X.Y.Z is ready — Restart to update"; **never while a session or Pomodoro run is in progress**. One click downloads, installs, reopens. |

### Decided in this plan (reopen in review if you disagree)

| Question | Decision | Why |
|---|---|---|
| Who builds releases | **GitHub Actions on a version tag**, never a local machine. | Same build every time; the signing key lives in GitHub secrets, not on two laptops. |
| The "go" button | Tag → workflow builds a **draft** GitHub Release → Lucas reviews and clicks **Publish** → desktop apps see it (the updater only reads published releases) and a second workflow deploys the web version to Vercel. | One deliberate action ships desktop and web together, at the same version. |
| Web deploys | **Only on a published release**, via the Vercel CLI from Actions. The Vercel project is **not** connected to the Git repo, so merges and PRs never deploy. | A merge to `master` must not reach friends before its migration is pushed and a release is cut. Also keeps PR previews from talking to the real server. |
| Windows code signing | **None** (Authenticode costs money). First install shows SmartScreen's "Windows protected your PC" once → "More info → Run anyway". Updates install without it. | No paid services. Said plainly in the invitation message. |
| Update signing | Tauri's free minisign key. **Lucas generates and keeps the private key** (password manager + GitHub secret). Public key committed in `tauri.conf.json`. | Losing the private key strands every install (they'd need a manual reinstall). Never committed, never on my side. |
| Signed update files | Produced **only in CI** (`--config` sets `bundle.createUpdaterArtifacts: true`). | With it on in `tauri.conf.json`, every local `tauri build` would fail without the private key. |
| Stable download link | The release also carries a copy named `Starkeep-setup.exe`, so `…/releases/latest/download/Starkeep-setup.exe` never changes. | One link to send friends, valid forever. |
| Update checks | Production desktop builds only (not `tauri dev`): ~10 s after launch, then every 6 h. "Later" hides it until next launch. | The app sits in the tray for days. Dev builds would otherwise be offered the published release. |
| Version | `npm run version:set -- X.Y.Z` updates `package.json`, `package-lock.json`, `tauri.conf.json`, `Cargo.toml`, `Cargo.lock`; the drift test extends to the Rust files; the release workflow refuses a tag that doesn't match. Shown in the Account panel ("Starkeep 0.1.0"). | Four files must agree; a friend saying which version they run makes support possible. |
| First releases | **v0.1.0**, then **v0.1.1** as the end-to-end update test, both before anyone is invited. | The only real proof of auto-update is updating a real install. |

## Outcomes

- O1. Anyone with the link can install the desktop app without a GitHub account.
- O2. An installed desktop app learns of a new version by itself and updates with one click, never mid-session, keeping its data and sign-in.
- O3. Anyone with the link can use the web version, connected to the hosted server, installable and offline-capable, with its existing update prompt.
- O4. A release is one deliberate action that ships desktop and web at the same version; nothing reaches friends from a mere merge.
- O5. Development and CI never touch the hosted server; local `tauri build` still works without the signing key.
- O6. Nothing regresses.

## Contracts

### PR 1 — `feat/release-updater` (the app side)

- **Rust** (`src-tauri/`): deps `tauri-plugin-updater = "2"`, `tauri-plugin-process = "2"`; register both in `run()` (updater via `tauri_plugin_updater::Builder::new().build()`). Capabilities (`capabilities/default.json`): `updater:default`, `process:allow-restart`.
- **`tauri.conf.json`**: `plugins.updater = { pubkey: "<Lucas's>", endpoints: ["https://github.com/lucashlc822/work-timer/releases/latest/download/latest.json"], windows: { installMode: "passive" } }`. `bundle.createUpdaterArtifacts` stays off (CI turns it on).
- **JS deps**: `@tauri-apps/plugin-updater`, `@tauri-apps/plugin-process`, imported only inside `shared/runtime/desktop.ts` (dynamic, like the existing Tauri imports).
- **Runtime port** (`src/shared/runtime/types.ts`, `web.ts`, `desktop.ts`):
  ```ts
  interface AvailableUpdate { version: string; install(): Promise<void> } // download, install, relaunch
  interface UpdaterPort { isSupported: boolean; check(): Promise<AvailableUpdate | null> }
  ```
  Web: `isSupported: false`, `check` → `null` (browser updates stay with the service worker). Desktop: `check()` wraps `check()` from the plugin (errors → `null`, logged); `install()` = `downloadAndInstall()` then `relaunch()`.
- **Shared busy check** (`src/shared/db/meta.ts`): `hasWorkInFlight(db): Promise<boolean>` (`activeSessionId` or `activeRun` present) plus `isAccountDbBound(): boolean` in `schema.ts`. `AccountPanel`'s `useBusy` switches to it (no behaviour change).
- **`src/app/DesktopUpdatePrompt.tsx`**: rendered in `App.tsx` beside the web `UpdatePrompt` when `isDesktop()` (main window only — the mini window branch renders neither). Checks when `import.meta.env.PROD`: 10 s after mount, then every 6 h. Visible only if an update exists, the user hasn't pressed "Later" this launch, and no work is in flight (live query over `hasWorkInFlight`; treated as idle when no account store is bound, i.e. on the sign-in screen). Copy: "Starkeep {version} is ready." [Later] [Restart to update] → "Updating…" → on failure "Couldn't update. Try again later." Same visual style as `UpdatePrompt`.
- **Version tooling**: `scripts/set-version.mjs` + `npm run version:set -- X.Y.Z` (rejects non-`x.y.z`); `src/shared/config/version.test.ts` drift test also checks `Cargo.toml` and the `starkeep` entry in `Cargo.lock`. Account panel footer: "Starkeep {APP_VERSION}".

### PR 2 — `feat/release-pipeline` (shipping)

- **`.github/workflows/release.yml`** — on `push: tags: ['v*']`, `permissions: contents: write`:
  1. `version` job (ubuntu): `node scripts/set-version.mjs --check ${{ github.ref_name }}` fails unless all five files say the tag's version.
  2. `desktop` job (windows): `npm ci`; `tauri-apps/tauri-action@v0` with `tagName`, `releaseName: 'Starkeep v__VERSION__'`, `releaseDraft: true`, `includeUpdaterJson: true`, `args: --config '{"bundle":{"createUpdaterArtifacts":true}}'`; env `GITHUB_TOKEN`, `TAURI_SIGNING_PRIVATE_KEY(_PASSWORD)`, `VITE_SUPABASE_URL`/`_PUBLISHABLE_KEY` from repo variables. Then `gh release upload <tag> Starkeep-setup.exe` (a copy of the NSIS installer).
- **`.github/workflows/deploy-web.yml`** — on `release: types: [published]`: checkout the release tag; `npm ci`; `npm run build` with the hosted `VITE_*` variables; `npx vercel deploy dist --prod --yes` with `VERCEL_TOKEN`/`ORG_ID`/`PROJECT_ID`. Fails loudly if a variable is missing (an unconfigured web build must never reach friends).
- `.gitignore`: `.vercel/`.
- **Docs**:
  - `RELEASING.md` — the checklist: (1) if the release needs a migration, `npx supabase db push` to the hosted project **first** (migrations are backward compatible); (2) `npm run version:set -- X.Y.Z` on a branch → PR → merge; (3) tag `vX.Y.Z` on `master` and push; (4) review the draft release; (5) **Publish**; (6) verify web + an installed app; (7) only raise `min_client_version` after the matching release is out. Plus: what to do if the signing key is lost.
  - `docs/invite-a-friend.md` — Lucas's steps (`npm run invite -- add <email>`) and a ready-to-send message: the web link, the stable installer link, the SmartScreen click-through, "on a Mac use the web version: Safari → File → Add to Dock", and that sign-up needs the invited address.
  - CLAUDE.md decisions: repo public; Vercel deploys only from published releases; desktop updates by notice + one click, never mid-session; no Authenticode (SmartScreen accepted); update-signing key custody; version tooling. Environment note: updater checks are production-only.
  - Architecture doc: Release row points here; hosting row Cloudflare → Vercel (superseded, with date).
  - `.env.example`: the CI variables and secrets, which are secret and which aren't.

## Edge cases decided

- Updater endpoint unreachable / GitHub down → `check()` returns null; no notice, retry in 6 h.
- Update downloaded but install fails → error text, app keeps running the old version.
- A release published with a broken web build → `deploy-web` fails before deploying (missing vars or build error); Vercel keeps serving the previous version.
- Friend on the sign-in screen → treated as idle, so an update is still offered.
- A draft release is invisible to the updater and to the stable link.
- `min_client_version` stays null until some release actually needs it.
